  # 선착순 쿠폰 발급 설계서

    
  ---

  ## 1. 문서 목적

    - 현재 구현된 **선착순 쿠폰 발급 흐름**을 자료구조 관점에서 명확히 설명한다.
    - 동시성/선착순 보장 수준, 실패 시나리오, 운영 포인트를 정리한다.
    
    ---

  ## 2. 시스템 개요

    - 사용자는 “쿠폰 발급 요청”을 보낸다.
    - 서버는 **유효성 검사** 후, 레디스 **요청 대기열(ZSET)** 에 사용자를 등록한다.
    - **스케줄러(1분 주기)** 가 발급 가능한 쿠폰들을 조회해, 요청 대기열에서 **선착순**으로 N명을 꺼내어 발급 처리한다.
    - 발급 성공/실패 결과는 레디스 **SET** 에 기록한다.

  ### 2.1 운영 관점 메모(트래픽 제어/학습 목적)

    - 본 설계에서 **Redis는 대용량 트래픽 제어/스로틀링을 위한 필터·완충 레이어**로 사용한다. 즉, 선착순 대기열(ZSET)을 통해 순간 폭주를 흡수하고, 빠른 멤버십 검사(SET)로 중복을 억제한다. **영속 로그 저장소로 사용하지 않는다.**
    - `coupon:{id}:requests`(ZSET) **대기열은 필수 상태**로, 선착순을 결정하는 핵심이다.
    - `coupon:{id}:issued` / `coupon:{id}:failed`(SET)는 **학습 관점에서 Redis 자료구조를 더 사용해보기 위한 보조 로그 저장소**로 둔 것이다. **실무에서는 메모리 비용/운영 비용 때문에 이런 로그성 데이터는 DB/데이터 레이크등 에 영속 저장**하는 편이 일반적이다. 
    - 권장 운영 아키텍처: **ZSET(대기열/트래픽 완충) + DB(발급 이력·실패 사유 영속) + 관측(메트릭/로그 시스템)**.

  ### 2.2 동작 설계

    - 사용자는 “쿠폰 발급 요청”을 보낸다.
    - 서버는 **유효성 검사** 후, 레디스 **요청 대기열(ZSET)** 에 사용자를 등록한다.
    - **스케줄러(1분 주기)** 가 발급 가능한 쿠폰들을 조회해, 요청 대기열에서 **선착순**으로 N명을 꺼내어 발급 처리한다.
    - 발급 성공/실패 결과는 레디스 **SET** 에 기록한다.

  ## 3. 주요 컴포넌트 및 책임

  ### 3.1 `CouponCacheRepository` (Infra/Redis)

    - Redis 접근을 캡슐화.
    - 요청 대기열(ZSET) 추가/조회/삭제, 발급 성공/실패 집합(SET) 기록 및 통계 제공.

  ### 3.2 `CouponRepositoryImpl` (Domain ↔ Infra 브릿지)

    - JPA 저장소(`CouponJpaRepository`, `CouponIssueJpaRepository`) + Redis 캐시(`CouponCacheRepository`)를 합성하여 도메인에서 요구하는 저장소 인터페이스 `ICouponRepository` 구현.

  ### 3.3 `CouponIssueProcessor` (Domain Service)

    - 단일 쿠폰 단위의 **발급 배치 처리** 책임.
    - 발급 가능 수량 계산 → ZSET에서 상위 N건 조회 → DB 트랜잭션으로 발급 → 결과를 Redis SET/요청 큐에 반영.

  ### 3.4 `CouponScheduler` (Application/Scheduling)

    - 1분 주기로 발급 가능한 쿠폰들을 조회하고 `CouponIssueProcessor`에 위임.
    - 동시 실행 방지를 위해 ShedLock 사용.

  ### 3.5 `requestConponIssue(...)` 

    - 단건 발급 **요청 수신** .
    - 쿠폰 유효성 + 중복 발급 여부 검사 → 요청 대기열 등록.

  ## 4. 데이터 모델 & 자료구조(REDIS)

  | 키 | 자료구조 | 멤버/값 | 의미 |
      | --- | --- | --- | --- |
  | `coupon:{couponId}:requests` | **ZSET** | **member = userId (Long), score = 요청시각(ms)** | 선착순 대기열 |
  | `coupon:{couponId}:issued` | **SET** | member = userId | 발급 성공 사용자 집합 |
  | `coupon:{couponId}:failed` | **SET** | member = userId | 발급 실패 사용자 집합 |

  > 선착순 근거: ZSET은 score 오름차순으로 정렬됨. ZRANGE 0..(N-1)은 가장 먼저 요청한 사용자부터 N명을 가져온다.

  ## 5. 처리 흐름(시퀀스)

  ### 5.1 사용자 요청 → 대기열 등록

    1. `requestConponIssue(command)`
        - `couponRepository.findById(...)`로 쿠폰 조회. 없으면 404.
        - `coupon.validateIssuable()`로 시간/상태 등 도메인 유효성 검사.
        - `couponRepository.isIssuedMember(couponId, userId)`로 이미 발급된 사용자면 409.
        - 통과 시, `couponRepository.addRequest(couponId, userId)` → `ZADD coupon:{id}:requests (score=System.currentTimeMillis(), member=userId)`.
    2. **결과**: 사용자 `userId`는 해당 쿠폰 대기열(ZSET)에 ‘요청시각’ 기준으로 줄을 선다.

  ### 5.2 스케줄러 배치 발급

    1. `CouponScheduler.issueCoupon()`가 1분마다 실행.
        - `findIssuableCoupons(now - 1분)`로 발급 가능한 쿠폰 목록 조회.
    2. 각 쿠폰에 대해 `CouponIssueProcessor.processCouponIssuance(coupon)` 실행.
        - `issuableCount` = `총수량 - 이미발급수량` (없으면 기본 10,000) → 음수/0이면 스킵.
        - `getRequestsByTimestamp(couponId, issuableCount)` → `ZRANGE coupon:{id}:requests 0..(limit-1) WITHSCORES`로 **선착순 상위 N건 조회(읽기)**
        - 각 요청에 대해:
            - `userRepository.findById(userId)`
            - `coupon.issueAt(user, 요청시각)` 실행(트랜잭션, 수량/기간/중복 보증)
            - 성공이면 `success`, 실패면 `failed` 목록에 적재
        - `saveResults(couponId, result, processedCount)`
            - 성공 목록 비어있지 않으면:
                - `SADD coupon:{id}:issued success...`
                - `ZREMRANGEBYRANK coupon:{id}:requests 0..(processedCount-1)`로 요청 큐 앞에서 **일괄 삭제**
            - 실패 목록 비어있지 않으면:
                - `SADD coupon:{id}:failed failed...`

  > 중요 포인트: 현재 삭제는 성공자가 1명 이상일 때만 수행되며, 삭제 수는 메서드 인자로 전달된 processedCount(일반적으로 issuableCount)를 사용.
  >

  ## 6. 선착순 보장 수준 & 동시성 고려

  ### 6.1 선착순 보장(현 구조)

    - ZSET의 score가 요청시각이고, `ZRANGE 0..(N-1)`로 상위 N건을 읽기 때문에 **대체로 선착순**으로 동작.
    - 단, 같은 사용자가 여러 번 요청하면 **기존 멤버의 score가 갱신**되어 줄의 뒤로 밀릴 수 있음(‘최초 요청 시각 고정’은 아님).

  ### 6.2 원자성

    - 현재는 `ZRANGE(읽기)` → 처리 → `ZREMRANGEBYRANK(삭제)`가 **두 단계**라 완전 원자적이지 않음.
    - 다중 인스턴스/장애 시 중복 처리 가능성이 이론적으로 존재.

  ### 6.3 스케줄러 잠금

    - ShedLock을 사용으로 여러 인스턴스의 요청을 한번만 처리함.

  ### 6.4 DB 최종 중복 발지방급

    - 최종적인 중복 발급 방지는 DB 제약(`coupon_issue(coupon_id, user_id) UNIQUE`)과 트랜잭션 내 수량 차감 로직으로 보증해야 함.

  ## 7. 예외/실패 시나리오

  | 시나리오 | 현재 동작 |
      | --- | --- |
  | 중복 발급 사용자 요청 | `isIssuedMember`로 차단(SET `issued`의 SISMEMBER) |
  | 같은 사용자가 여러 번 요청 | ZSET 멤버 동일 → score가 **갱신**되어 후순위로 밀림 |
  | 배치에서 전원 실패 | 성공 목록이 비어 있어 **삭제 미수행** → 동일 요청이 다음 배치에 다시 시도됨 |
  | 배치 처리 중 장애 | `ZRANGE`만 진행된 상태에서 장애 시 큐에는 남아 있으므로 재처리 가능(중복 가능성은 도메인/DB가 차단해야 함) |
  | 레디스/DB 부분 실패 | 현재는 순서를 보장하는 트랜잭션 경계가 다르므로 불일치 가능(운영에서 모니터링 및 보정 필요) |

  ## 8. 운영/관측 포인트

    - **메트릭**
        - 요청 큐 길이: `ZCARD coupon:{id}:requests`
        - 발급 성공/실패 수: `SCARD issued/failed`
        - 배치당 처리 건수, 처리 시간, 예외율
    - **로그/알람**
        - `issueCoupon` 시작/종료, 쿠폰별 처리 결과 요약
        - `CouponIssueProcessor` 예외 스택, 실패 이유 Top-N 집계
    - **키 정리/TTL(선택)**
        - 쿠폰 기간 종료 후 `issued/failed/requests` 키 TTL 설정 또는 주기적 삭제

    ---

  ## 9. 성능/복잡도(빅오)

    - 요청 등록: `ZADD` → **O(log N)**
    - 상위 N 조회: `ZRANGE 0..(N-1)` → **O(log N + N)**
    - 일괄 삭제: `ZREMRANGEBYRANK 0..(N-1)` → **O(log N + N)**
    - 성공/실패 기록: `SADD K` → **O(K)**
    - 중복 확인: `SISMEMBER` → **O(1)**

  > N은 해당 쿠폰의 대기열 크기.
