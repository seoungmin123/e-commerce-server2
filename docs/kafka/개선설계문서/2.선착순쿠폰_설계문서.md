# 선착순 쿠폰 발급 시스템 설계문서

## 1. 개요

### 1.1 프로젝트 배경
전자상거래 플랫폼에서 마케팅 이벤트로 진행하는 선착순 쿠폰 발급 시스템은 높은 동시성과 정확한 순서 보장이 필요한 핵심 기능입니다. 기존 Redis 기반 시스템에서 발생한 성능 병목과 데이터 일관성 문제를 해결하기 위해 Kafka 기반 이벤트 드리븐 아키텍처로의 전환을 진행합니다.

### 1.2 요구사항 정의

#### 기능적 요구사항
- 사용자는 선착순으로 할인 쿠폰을 발급받을 수 있습니다
- 주문 시 유효한 할인 쿠폰을 제출하면 전체 주문금액에 대해 할인 혜택을 받을 수 있습니다
- 같은 사용자가 동일 쿠폰을 1번만 발급받을 수 있습니다
- 쿠폰 발급 요청 후 결과를 확인할 수 있습니다

#### 비기능적 요구사항
- **동시성**: 10,000명 이상의 동시 요청 처리
- **정확성**: 쿠폰 중복 발급 0%, 선착순 정확도 99.9%
- **응답성**: 요청 접수 응답 시간 100ms 이하
- **가용성**: 99.9% 이상의 서비스 가용성
- **멱등성**: 동일 요청의 중복 처리 방지

### 1.3 기술적 과제
- 대용량 동시 요청에 대한 안전한 동시성 제어
- 선착순 순서의 정확한 보장
- 시스템 장애 시에도 데이터 손실 방지
- 사용자 경험을 위한 실시간 상태 피드백

## 2. 시스템 분석

### 2.1 기존 시스템 분석 (Redis 기반)

#### 아키텍처
```
사용자 요청 → Service → Redis 대기열 추가 → Event Publisher → Kafka
            ↓
        스케줄러(1분마다) → Redis 대기열 조회 → 메모리에서 쿠폰 발급
            ↓                                    ↓
        Event Publisher → Kafka → Consumer → DB 저장
```

#### 기존 코드 특징
- **CouponService.requestCouponIssue()**: Redis ZSet에 타임스탬프 기반 요청 저장
- **CouponScheduler**: 1분마다 발급 가능한 쿠폰 조회하여 배치 처리
- **CouponIssueProcessor**: Redis에서 선착순 사용자 조회 후 메모리에서 쿠폰 발급
- **CouponEventConsumer**: Kafka 메시지 수신하여 DB에 최종 저장

### 2.2 문제점 도출

#### 성능 문제
- **처리 지연**: 스케줄러 주기(1분)로 인한 최대 1분 지연
- **이중 처리**: Redis 처리 + Kafka 처리로 인한 복잡성
- **메모리-DB 불일치**: 메모리 상태와 실제 DB 상태 간 불일치 가능성

#### 구조적 문제
- **책임 과중**: CouponEventConsumer가 6가지 책임을 모두 담당
- **단일 장애점**: Redis 장애 시 대기열 데이터 손실 위험
- **사용자 경험**: 요청 후 결과를 알 수 없는 구조

### 2.3 개선 목표 설정
- 실시간 처리로 응답 시간 단축
- 단일 책임 원칙 적용으로 유지보수성 향상
- DB 기반 원자적 연산으로 데이터 일관성 보장
- 폴링 시스템으로 사용자 경험 개선

## 3. 기술 선택 및 설계 방향

### 3.1 아키텍처 패턴 선택

#### Event-Driven Architecture 선택 이유
- **확장성**: 컴포넌트 간 느슨한 결합으로 독립적 확장 가능
- **내구성**: Kafka의 메시지 영속성으로 데이터 손실 방지
- **관찰성**: 이벤트 스트림을 통한 시스템 상태 모니터링

#### CQRS 패턴 적용
- **Command**: 쿠폰 발급 요청 (Write)
- **Query**: 쿠폰 상태 조회 (Read)
- **분리 효과**: 읽기/쓰기 최적화로 성능 향상

### 3.2 기술 스택 결정

#### 동시성 처리: DB 원자적 연산
```sql
-- 선택 이유: 단순성, 정확성, 표준 SQL
UPDATE coupon SET issued_quantity = issued_quantity + 1 
WHERE id = ? AND issued_quantity < total_issue_quantity;
```

**장점**
- 학습 곡선이 낮고 디버깅 용이
- ACID 속성으로 완벽한 일관성 보장
- 표준 SQL로 DB 종속성 최소화

**단점**
- 높은 동시성에서 DB 부하 증가
- Redis 대비 상대적으로 느린 성능

#### 캐시 레이어: Redis
```redis
# 빠른 사전 검증 및 상태 관리
SISMEMBER coupon:1:issued user123
SET user:123:coupon:1:status "PENDING" EX 3600
```

#### 메시징: Apache Kafka
- **내구성**: 메시지 영속화로 데이터 손실 방지
- **순서 보장**: 파티션 단위 순서 보장
- **확장성**: 파티션 기반 수평 확장

### 3.3 트레이드오프 분석

| 측면 | 기존 (Redis) | 개선 (DB+Redis) | 트레이드오프 |
|------|-------------|------------------|-------------|
| **성능** | 매우 빠름 (1ms) | 빠름 (20ms) | 성능 vs 정확성 |
| **정확성** | 높음 (95%) | 매우 높음 (99.9%) | 속도 vs 일관성 |
| **복잡도** | 높음 | 중간 | 복잡성 vs 유지보수성 |
| **장애 복구** | 어려움 | 쉬움 | 성능 vs 안정성 |

#### 개선된 구조
```
사용자 요청 → Service → Redis 빠른 검증 → Event Publisher → Kafka → Consumer → DB 원자적 처리
            ↓                                                          ↓
        즉시 요청ID 반환                                            상태 업데이트
            ↓                                                          ↓
```

- **기존**: Redis ZSet 타임스탬프 → 스케줄러 → 메모리 발급

### 6.1 요청 접수 단계
```java
@Transactional
public String requestCoupon(Long userId, Long couponId) {
    String requestId = UUID.randomUUID().toString();
    
    // 1. Redis에서 빠른 사전 검증
    if (!canRequest(userId, couponId)) {
        throw new ApiException(ALREADY_ISSUED_OR_EXHAUSTED);
    }
    
    // 2. 요청 상태를 Redis에 저장 (폴링용)
    setUserStatus(userId, couponId, "PENDING", requestId);
    
    // 3. Kafka 이벤트 발행
    eventPublisher.publishEvent(
        CouponEvent.Requested.of(requestId, couponId, userId)
    );
    
    return requestId;
}
```

### 6.2 실제 처리 단계
```java
@Transactional
public CouponIssueResult tryIssueCoupon(Long couponId, Long userId) {
    try {
        // 1. 원자적 수량 증가 (DB 레벨에서 동시성 처리)
        int updated = couponRepository.incrementIssuedQuantityIfAvailable(couponId);
        if (updated == 0) {
            return CouponIssueResult.failed("쿠폰이 모두 소진되었습니다.");
        }
        
        // 2. 쿠폰 발급 기록 생성 (유니크 제약으로 중복 방지)
        CouponIssue couponIssue = CouponIssue.create(coupon, user);
        couponIssue = couponIssueRepository.save(couponIssue);
        
        return CouponIssueResult.success(couponIssue);
        
    } catch (DataIntegrityViolationException e) {
        // 유니크 제약 위반 = 이미 발급받음
        return CouponIssueResult.failed("이미 발급받은 쿠폰입니다.");
    }
}
```

```java
// 10,000명 동시 요청 테스트
ExecutorService executor = Executors.newFixedThreadPool(1000);
CountDownLatch latch = new CountDownLatch(10000);

for (int i = 0; i < 10000; i++) {
    executor.submit(() -> {
        try {
            couponService.requestCoupon(userId, couponId);
        } finally {
            latch.countDown();
        }
```

## 8. 운영 방안

### 8.1 모니터링 지표

#### 비즈니스 메트릭
- **쿠폰 발급률**: 요청 대비 성공적 발급 비율
- **중복 발급 건수**: 시간당 중복 발급 시도 건수
- **평균 대기 시간**: 요청부터 결과 확인까지 시간

#### 시스템 메트릭
- **Kafka Consumer Lag**: 메시지 처리 지연 시간
- **Redis 응답 시간**: 캐시 조회 성능
- **DB Connection Pool**: 데이터베이스 연결 상태

### 8.2 알람 정책
```yaml
alerts:
  - name: "쿠폰 중복 발급 감지"
    condition: "duplicate_issue_count > 10"
    severity: "CRITICAL"
  
  - name: "Kafka Consumer Lag 증가"
    condition: "consumer_lag > 1000"
    severity: "WARNING"
  
  - name: "Redis 응답 지연"
    condition: "redis_response_time > 100ms"
    severity: "WARNING"
```

### 8.3 장애 대응 방안

#### Redis 장애
- **영향**: 사전 검증 불가, 상태 조회 불가
- **대응**: DB 직접 조회로 fallback
- **복구**: Redis 재시작 후 캐시 warming

#### Kafka 장애
- **영향**: 비동기 처리 중단
- **대응**: 요청 접수는 계속, 처리는 지연
- **복구**: Kafka 복구 후 메시지 자동 처리

#### DB 장애
- **영향**: 전체 서비스 중단
- **대응**: Read Replica로 조회 기능 유지
- **복구**: 마스터 DB 복구 후 정상화
