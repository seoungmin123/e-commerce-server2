## **1\. Kafka란 무엇인가?**

Kafka는 **분산 메시지 플랫폼**이다.

MSA 환경에서 한 서비스가 메시지를 던지면(Producer), Kafka Broker가 이를 안전하게 저장하고 다른 서비스(Consumer)들이 가져가서 처리하는 구조이다.

Kafka는 **큐와 비슷한 구조**를 가진다. 메시지가 들어오면 **파티션**이라는 여러 줄로 나뉘어 저장되고, 같은 줄 안에서는 순서를 보장하며 차례대로 처리된다.

즉, 한쪽에서는 순서를 지키고, 다른 쪽에서는 여러 줄을 동시에 처리하면서 병렬성을 얻을 수 있다.

---

## **2\. Kafka의 특징**

-   **로그 기반 저장(Log-based Storage)**
    -   Kafka는 메시지를 지우지 않고 디스크에 **순차적으로 기록(append-only)**
    -   속도가 빠르고 필요한 순간 과거 메시지를 **오프셋(offset)** 기준으로 다시 읽을 수 있음 (리플레이 가능)
-   **분산 처리 구조**
    -   메시지를 담는 단위: **토픽(topic)**
    -   토픽은 다시 여러 \*\*파티션(partition)\*\*으로 나뉨
    -   병렬 처리 가능, 서비스가 많아져도 **수평 확장 용이**

---

## **3\. Kafka 핵심 구성요소**

-   **Producer**: 이벤트 발행 (예: 주문 서비스가 “주문 생성됨” 메시지 발행)
-   **Broker**: Kafka 서버. 메시지를 저장 및 전달
-   **Consumer**: 이벤트를 구독해 처리 (예: 결제 서비스가 “주문 생성됨” 메시지 처리)
-   **Consumer Group**: 여러 컨슈머를 묶어 병렬 처리 단위를 맞춤. 파티션이 나눠져 각자 담당
-   **Offset**: 컨슈머가 어디까지 읽었는지 표시하는 위치 값

---

## **4\. Kafka의 강점**

-   **고가용성 & 확장성**
    -   **Replication**: 각 파티션은 Leader + Follower 복제본을 가짐 → 서버 하나가 죽어도 데이터 보존
    -   **Failover**: Leader 장애 시 Follower가 자동 승격
        -   Zookeeper 방식: Zookeeper가 Leader 선출
        -   KRaft 방식: Raft 합의 알고리즘으로 Controller Quorum이 투표
        -   (최근엔 KRaft 방식이 주로 사용됨)
    -   **Rebalancing**: 컨슈머 수 변화 시 파티션 담당 재분배
    -   **확장성**: 브로커(서버)나 파티션을 무중단 확장 가능

Kafka는 **장애에 강하고 트래픽 확장이 쉽다**.

또한 MQ와 달리 지난 이벤트를 지우지 않고 **다시 읽을 수 있다**.

---

## **5\. 이벤트 처리 방식**

이벤트 기반 시스템을 설계하다 보면 단순히 메시지를 주고받는 수준을 넘어서 1. 어떻게 상태를 관리할지, 2. 분산된 트랜잭션을 어떻게 맞출지, 3. 메시지가 유실되거나 중복되면 어떻게 대응할지 같은 문제가 따라온다.

Kafka는 이런 문제를 해결할수있는 여러 패턴과 전달 보장방식을 제공한다.

### **5-1. 이벤트 소싱 & CQRS**

많은 시스템은 단순 현재상태만 데이터 베이스에 저장한다. 그런데 분산환경에서는 어떻게 만들어졌는지가 중요할때가있다.

(누가발행했는가?) 이벤트 소싱은 상태를 직접 저장하지않고 발생한 이벤트들의 기록을 그대로 저장해두는 방식이다.

덕분에 과거 이벤트를 재생하면 언제든 동일한 상태를 복원할 수 있다. CQRS는 읽기와 쓰기를 분리하는 전략이고 , Kafka 이벤트를 소비해 읽기 전용 모델을 따로 구성 할 때 활용한다고한다.

-   **이벤트 소싱(Event Sourcing)**: 상태를 직접 저장하지 않고 이벤트 로그를 기록해두는 방식. 과거 이벤트 재생으로 상태 복구 가능
-   **CQRS**: 쓰기(Command)와 읽기(Query) 분리. Kafka 이벤트를 소비해 읽기 모델을 따로 구축할 때 활용

### **5-2. 트랜잭션/일관성**

하나의 인스턴스안에서 트랜잭션을 관리하면 단순하다. 하지만 MSA 환경에서 주문-재고-결제처럼 여러 도메인 서비스가 얽히면 문제가 복잡해진다. Kafka와 같은 이벤트 기반 시스템에서는 이런 분산 트랜잭션을 사가패턴을 활용해 해결한다.

-   **사가 패턴(Saga Pattern)**
    -   **코레오그래피(Choreography)**: 서비스들이 이벤트를 직접 주고받음 → 분산 제어
    -   **오케스트레이션(Orchestration)**: 중앙 오케스트레이터가 전체 흐름 제어 → 단일 진입점
-   **보상 트랜잭션(Compensating Transaction)**: 실패 시 앞서 한 작업을 취소/되돌림
-   **2PC(이단계 커밋)**: DB 수준 분산 트랜잭션 (Kafka와 비교할 때 언급됨

### **5-3. 메시지 전달 보장 (Delivery Semantics)**

MSA환경에서 네트워크 유실문제를 생각하지않을수없다. 또한 서버는 언제든 장애가 날 수있기때문에(그러면안됨ㅋ) Kafka는 메시지를 얼마나 확실하게 전달할지 선택하게된다. 결국 보장 수준은 오프셋을 언제 저장(commit)하냐에 따라 달라진다.

-   **At-most-once**: 최대 1번 (메시지 유실 가능)
-   **At-least-once**: 최소 1번 (중복 가능 → 멱등성 필요)
-   **Exactly-once**: 정확히 1번 (트랜잭션 + 멱등성 이용, 비용과 복잡성 높음)
-   **멱등성(Idempotence)**: 중복 메시지가 와도 결과가 꼬이지 않게 설계 (Inbox 테이블 활용 등)

## **6\. Inbox & Outbox 패턴**

MSA 환경에서 트랜잭션 불일치를 막는 핵심 패턴이다. 단순히 메시지만 주고받으면 정합성 문제가 생길 수 있다. 예를 들어, 주문 서비스가 DB에는 주문을 저장했는데 이벤트 발행에 실패한다면 다른 서비스는 주문 사실을 모르게 된다. 반대로 이벤트만 발행되고 서비스로직이 실패하면 실제로는 없는 주문이 생겨버린다. 이를 막기 위해 발행 측은 Outbox 패턴을 써서 “DB 저장 + 이벤트 기록”을 같이 처리하고 소비 측은 Inbox 패턴을 써서 이벤트를 안전하게 기록하고 중복은 걸러내는 방식을 사용한다.

### **6-1.  Outbox 패턴 (발행 측)**

-   DB 저장 + 이벤트 발행을 원자적으로 묶기 어려움
-   해결: **Outbox 테이블**에 이벤트를 저장 후, Worker가 Kafka로 발행

### **6-2. Inbox 패턴 (수신 측)**

-   Kafka에서 이벤트를 받으면 **Inbox 테이블**에 기록
-   중복 이벤트 무시 → 멱등성 보장

### **6-3. 조합**

-   발행 측: Outbox
-   수신 측: Inbox
-   이벤트 유실/중복 방지 → 정합성 확보

(실무에서는 성능/구현 난이도로 인해 Inbox/Outbox 없이 신뢰 기반 구현하는 경우도 있음)

## **7\. 토픽/파티션 관리 전략**

kafka를 도입 후 처음에는 메시지가 젤 오가네! 하고 끝나지만 트래픽이 커지고 컨슈머가 늘어나면 성능병목이 생기게된다.

파티션은 kafka의 병렬성 단위이자, 동시에 순서를 보장하는 단위이다.

-   파티션수를 너무 적게 주면 → 동시성 제한 , 성능저하
-   파티션 수 너무 많이주면 → 리벨런싱 비용이 커져서 운영이 복잡해진다.

따라서 적절한 파티션 수와 키 전력을 선택하는것이 성능 최적화의 핵심이다.

-   **파티션 수 결정**
    -   처리량 = 파티션 수 × 컨슈머 수
    -   적으면 확장성 부족, 많으면 리밸런싱 비용 ↑
-   **파티션 키 전략**
    -   순서 불필요 → Round Robin, 해시 기반
    -   순서 필요 → userId/orderId 같은 키 고정
    -   주의: 특정 키 쏠림(hot key) 방지
-   **토픽 설정**
    -   Replication Factor: 3개 이상 권장
    -   Retention: 시간/용량 기반
    -   Compaction: 키별 최신 상태만 유지
-   **파티션 증설**
    -   중간 증설 시 키-파티션 매핑 달라져 순서 깨짐
    -   → 처음부터 여유 있게 설계
-   **운영 고려사항**
    -   파티션 수 ↑ → 리밸런싱 시간 ↑
    -   Consumer Lag 모니터링 필수
    -   토픽 수 과다 → 메타데이터 관리 비용 ↑

---

## **정리**

Kafka는 단순 메시지 큐가 아닌 **로그 기반 분산 스트리밍 플랫폼**이다.

-   **파티션을 통한 병렬성과 순서 보장**
-   **Inbox/Outbox 패턴으로 정합성 확보**
-   **운영 단계에서 Lag 모니터링 및 보상 트랜잭션 설계 필요**
